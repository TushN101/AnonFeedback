# AnonFeedback — Project Report

> A college mini-project demonstrating how a college can verify that faculty
> feedback comes from an eligible student, **without** being able to link a
> feedback response to that student's identity through the intended protocol —
> using a Zero-Knowledge Proof.

---

## 1. Problem statement

College faculty feedback systems today face a structural trust problem:

- **Google Forms / Microsoft Forms**, when run by an institution account, can
  silently enable email collection, view respondent timestamps, and correlate
  responses with login sessions. Even when the institution *promises*
  "responses are anonymous," students have only a policy guarantee — there is
  no technical barrier preventing the form owner from re-identifying
  respondents.
- **Physical paper forms** rely on physical handling (no names on paper,
  shuffled collection box). This is hard to audit and breaks down at scale or
  in small classes where handwriting or content gives the student away.
- **Identified online forms** verify eligibility cleanly (each respondent is a
  real student) but every response is permanently tied to an identity in the
  backend, chilling honest feedback.

The core tension is **eligibility verification vs. response anonymity**. The
college wants to reject feedback from non-students; students want a *technical*
(not merely policy-based) guarantee that their feedback cannot be traced back
to them.

AnonFeedback explores whether **Zero-Knowledge Proofs (ZKPs)** can resolve
this tension. The college verifies that *some* eligible student produced the
feedback, but the proof itself does not reveal *which* one.

### Scope

This is a **college mini-project and demonstrator**. It is not
production-ready, not hardened against a determined deanonymization adversary,
and not a substitute for a formally audited anonymous-feedback system. The
goal is to make the cryptographic workflow concrete, runnable, and
understandable. Every security claim below is qualified by §6.

## 2. Cryptographic approach

### 2.1 What we proved

A 1-out-of-n **disjunctive Sigma-protocol** — the classic Cramer–Damgård–
Schoenmakers (CDS) "proofs of partial knowledge" construction — made
non-interactive via the **Fiat–Shamir heuristic**.

**Statement proved:** *"I know an integer `x` such that `g^x == Y_j` for some
`j` in the public eligible set `S = {Y_1, …, Y_n}` — but I do not reveal
which `j`."*

The construction is well-known in the cryptography literature (Cramer,
Damgård, Schoenmakers, *Proofs of Partial Knowledge*, CRYPTO 1994). It is
*not* a novel invention; the educational contribution here is a transparent,
minimal, auditable Python implementation.

### 2.2 Why not a heavier tool?

We surveyed zk-SNARKs, Bulletproofs, Idemix, BBS+ anonymous credentials, and
ring-signature libraries. Each either requires heavyweight tooling (trusted
setups, circuit compilers, pairing-friendly curves), pulls in
research-grade / unmaintained Python packages, or hides the cryptographic
core behind a black box — defeating the educational goal. The CDS proof is
small enough to implement in ~150 lines of pure Python (stdlib + hashlib
only), so every step is inspectable.

### 2.3 Group setup

- `p` — a **1024-bit safe prime** (`p = 2q + 1`, both `p` and `q` prime).
- `q` — the prime `(p-1)/2`; the subgroup of quadratic residues mod `p` has
  order `q`.
- `g` — a generator of the order-`q` subgroup.

Parameters are hardcoded in `zkp/params.py` (generated by
`scripts/generate_safe_prime.py`). **1024 bits is a demo compromise** for
generation speed; a production system would use 2048+ bits or, better, a
prime-order elliptic-curve group of order ~2^256. See §6 L1.

### 2.4 Protocol

**Setup & issuance.** Each student has a secret scalar `x_i` and a public key
`Y_i = g^{x_i} mod p`. The college adds `Y_i` to the public eligible set `S`.
The college sees the student's name only at this step.

**Proof generation.** To submit feedback `F` for course `C`, the student
builds a 1-out-of-n OR proof:

- For each simulated index `j ≠ k`: pick random `c_j, s_j ∈ Z_q`, compute
  `R_j = g^{s_j} · Y_j^{-c_j}`.
- For the real index `k`: pick random `r_k`, compute `R_k = g^{r_k}`.
- Fiat–Shamir challenge:
  `c = H("anonfeedback.v1" ‖ R_1 ‖ … ‖ R_n ‖ S ‖ feedback_context)`,
  where `feedback_context = "feedback:{C}:{SHA-256(F)}"`.
- `c_k = c − Σ_{j≠k} c_j  mod q`
- `s_k = r_k + c_k · x_k  mod q`

The published proof is `π = (c, ((R_1, c_1, s_1), …, (R_n, c_n, s_n)))`.

**Verification.** The college:

1. Recomputes the Fiat–Shamir challenge from the transcript and checks it
   equals `c`.
2. Checks `Σ_j c_j ≡ c mod q`.
3. For each `j`, checks `g^{s_j} ≡ R_j · Y_j^{c_j} mod p`.

If all three pass, the verifier is convinced that the prover knew the
discrete log of some `Y_j ∈ S`. The distribution of the transcript is
statistically independent of `k`, so the proof reveals nothing about which.

The critical property: **at verification time, the verifier consults only the
public set `S`.** The name↔key table used at issuance is not consulted and
plays no role in storage.

### 2.5 Nullifier for duplicate prevention

The current version extends the basic OR proof with a **course-scoped
nullifier** so the server can reject duplicate submissions for the same
(student, course) pair — without revealing the student's identity and
without introducing a link between the student's credential and their
feedback.

**Construction.** A second independent generator `G2` is derived via a
nothing-up-my-sleeve hash (see `zkp.group.hash_to_subgroup`). Its discrete
log with respect to `G` is unknown. For each course, a per-course nullifier
base `h = G2^{t_course}` is computed where `t_course = H("nullifier" ‖ course)`.

The student publishes a nullifier `N = h^{x_k}` alongside their OR proof.
The proof is extended with a **Chaum–Pedersen equality proof** at each
component: in addition to `R_j = g^{r_j}` (the existing Schnorr commitment),
the prover publishes `M_j = h^{r_j}` for the real index, and the verifier
checks both `g^{s_j} ≡ R_j · Y_j^{c_j}` AND `h^{s_j} ≡ M_j · N^{c_j}`. This
proves that `N = h^{x_k}` for the *same* `x_k` whose knowledge of
`Y_k = g^{x_k}` is proved — so a malicious student cannot lie about `N` to
bypass dedup.

**Properties.**

* `N` is **deterministic in (student_secret, course)** → the server stores
  `N` and rejects a second submission with the same `N` for the same course
  (HTTP 409 Conflict).
* `N` is **unlinkable across courses** → `h` differs per course, so under DDH
  `N_DBMS` and `N_OS` for the same student are pseudorandom and unlinkable.
* `N` is **unlinkable across students** → different `x_k` give different `N`.
* `N` is **not invertible to identity** → the server cannot test `N` against
  each `Y_j` to recover `k`, because that would require knowing `log_g(h)`,
  which is unknown (since `log_g(G2)` is unknown by construction).

The nullifier IS stored with the feedback record (for dedup) but is NOT
exposed on the public feedback board — only the admin sees it (for audit)
via `FeedbackRecord.admin_dict`. The nullifier is NOT a student identifier.

### 2.6 What binds the proof to the feedback?

The Fiat–Shamir transcript includes `SHA-256(feedback)`. A proof generated
for feedback `F` cannot be replayed against a different feedback `F'` — the
challenge will not recompute. Tests in `tests/test_e2e.py` verify this
(`test_replay_with_different_feedback_rejected`,
`test_replay_with_different_course_rejected`).

### 3.1 Module responsibilities (SOLID)

- `zkp/` — pure cryptography. No Flask, no I/O. Testable in isolation.
- `credential/` — orchestrates the protocol on top of `zkp/`. Knows about
  "students" and "eligible sets" but not about HTTP.
- `server/` — HTTP transport. Thin: parse JSON, delegate to `credential/`,
  render templates. No crypto logic here.
- `templates/` + `static/` — presentation only.

This separation makes the cryptographic core testable without spinning up a
server, and the server testable without re-implementing crypto.

### 3.3 On the `/api/student/prove` helper

In a "real" deployment, the student would generate the proof entirely
client-side in JavaScript. For an educational Python demo, doing 1024-bit
modular arithmetic and Fiat–Shamir transcripts in JS is busywork that adds
little pedagogical value and risks subtle bugs. We therefore run the same
`credential.build_proof` code server-side as a **stateless helper**: the
endpoint does not store the secret, the feedback, or the proof — it returns
the proof to the student's browser, which then submits it via `/api/submit`.

This is a documented demo simplification, not a security claim. The
server-side helper does not break unlinkability: it sees the secret only
during the prove call (which the student made voluntarily), and the secret is
not persisted. The verification path still consults only the public set `S`.

## 4. Workflow (demo)

### 4.1 Roleplay

There is no real college authentication system. We roleplay:

- **The college / registrar** is whoever opens `/admin`. There is no SSO; the
  demo trusts the admin to enter legitimate student names.
- **Students** are simulated by anyone with the `/student` URL and a secret.
- The "issuance channel" is copy-paste: admin clicks "Issue," gets a secret,
  and is told to paste it to the student out-of-band.

### 4.2 Walkthrough

1. Open `/admin`. Issue credentials for a few students. The system generates a
   fresh secret `x` for each, computes `Y = g^x`, adds `Y` to the public
   eligible set `S`, and returns the secret for the admin to forward.
2. Open `/student` in another tab (or browser). Paste the secret, pick a
   course, write feedback, click "Generate proof & submit."
3. The student UI calls `/api/student/prove` (stateless helper) to build the
   proof, then `/api/submit` to verify and store.
4. Open `/feedback`. The submitted feedback appears, marked verified. No
   identity is shown.
5. Try tampering: edit the feedback text after proof generation, and the
   submission is rejected (the Fiat–Shamir challenge won't recompute).

A `demo-secrets.txt` file is written to the working directory on first run
with the pre-seeded students' secrets, so the demonstrator can hand them out
immediately.

## 6. Security approach, assumptions, and limitations

We are precise about what is a *cryptographic guarantee* and what is an
*assumption* or *limitation*.

### 6.1 Cryptographic guarantees (under the stated assumptions)

1. **Completeness.** An honest student who knows a valid `x_k` with
   `Y_k ∈ S` produces an accepted proof with probability 1.
2. **Soundness.** A party who does not know any discrete log of any `Y_j ∈ S`
   cannot produce an accepting proof, except with probability ≤ 2^{-256}
   (SHA-256 output space). Relies on DL hardness in the order-`q` subgroup
   and the random-oracle model for Fiat–Shamir.
3. **Zero-knowledge / unlinkability of the proof transcript.** The
   distribution of `π` is statistically independent of the prover's index
   `k`. Two proofs from the same student are computationally indistinguishable
   from two proofs by different students. This is a property of the *proof
   transcript itself*.

These are genuine cryptographic properties of the CDS construction. They are
conditional on the assumptions in §6.2.

### 6.2 Assumptions

- A1. Discrete logarithm in the chosen subgroup is intractable for the
  adversary class we care about (educational threat model). 1024 bits is
  borderline; see §6.3 L1.
- A2. SHA-256 behaves as a random oracle (Fiat–Shamir heuristic).
- A3. The admin's issuance table (name ↔ public key) is not consulted at
  verification time and is not leaked.
- A4. `secrets` (OS CSPRNG) is secure.
- A5. The transport between admin and student for handing over `x_i` is
  out-of-band and not observed by the server.
- A6. The server does not keep per-request logs that include `x_i`.

### 6.3 Limitations (NOT solved by the ZKP)

- **L1 — Parameter size.** 1024-bit finite-field discrete log is at the edge
  of feasibility for well-resourced adversaries (cf. the Logjam paper). A
  real deployment would use 2048+ bits or an elliptic-curve group.
- **L2 — IP tracking.** The Flask server sees the submitter's IP. The ZKP
  does not hide network metadata. A real deployment would route submissions
  over Tor or a mixnet.
- **L3 — Timing correlation.** If the admin correlates issuance time, IP, and
  submission time, unlinkability is defeated by metadata. The ZKP only
  protects the cryptographic link.
- **L4 — Small eligible sets.** If `|S| = 1`, the proof trivially identifies
  the student. The demo requires `|S| ≥ 3` before accepting submissions, with
  a UI warning. This is a mitigation, not a fix.
- **L5 — Small respondent groups.** Even with a large `S`, if only one
  student submits feedback in a course, the feedback is effectively
  identified. Fundamental; cannot be fixed cryptographically.
- **L6 — Identifying content.** A student who writes "I'm the only one who
  got an A+" has identified themselves. No cryptographic protocol can prevent
  this. The UI shows a reminder.
- **L7 — Replay of identical feedback.** Proofs are non-deterministic, so two
  identical feedback payloads produce two different valid proofs. The server
  cannot cryptographically tell they came from the same student. We could add
  a nullifier `N = H(x_i ‖ course_id)` to enforce one-feedback-per-student-
  per-course — but a stable nullifier would itself become a linkable
  pseudonym across courses. The demo does not use nullifiers.
- **L8 — Server-side logging.** Flask/Werkzeug default request logging writes
  IP + timestamp + path to stdout. The demo disables this in `app.py`. Any
  reverse proxy in front must be configured similarly.
- **L9 — Single-server trust.** All state lives in one Flask process. A
  compromised server can DoS, reject valid proofs, or alter stored feedback.
  It cannot, however, learn the prover's identity from a valid proof
  transcript alone (assuming A3 holds and metadata correlation is off the
  table, which L2/L3 concede).
- **L10 — No formal proof.** The CDS construction is well-studied, but our
  implementation has not been formally verified. We rely on tests + code
  review.

### 6.4 What is NOT claimed

- We do **not** claim unlinkability against a network-level adversary.
- We do **not** claim protection against a malicious admin who records
  per-request IP and timestamps.
- We do **not** claim protection against a small eligible set or a small
  respondent group.
- We do **not** claim protection against self-identifying feedback content.
- We do **not** claim the demo is ready for real-world deployment.

## 7. Comparison with Google Forms, Microsoft Forms, and physical forms

| Property | Google Forms (institution account) | Microsoft Forms (institution account) | Physical paper forms | **AnonFeedback (this demo)** |
|---|---|---|---|---|
| Eligibility verification | Sign-in required; verified by Google account. | Sign-in required; verified by Microsoft account. | None by default; relies on physical collection. | **Cryptographic**: ZKP of membership in the eligible set `S`. |
| Identity captured at submission time | Yes (account email in the form-owner's backend, even if "record email" is off — owner can re-enable silently). | Yes (Microsoft account; admin can export responses with names). | No (if no name field). | **No**: the verification path consults only the public set `S`; no identity is stored with the feedback. |
| Anonymity guarantee | Policy-based (form owner's promise + Google's UI). Breaks if owner re-enables email collection. | Policy-based. | Physical-handling-based. Hard to audit. | **Cryptographic** (within §6's stated assumptions): the proof transcript does not reveal which student. |
| Can the form owner re-identify respondents later? | Yes — backend records exist. | Yes. | Only if names were collected or content identifies the student. | No — not from the proof transcript. (Metadata attacks still apply; see §6.3 L2/L3.) |
| Single-submission enforcement | Yes (by account). | Yes. | Hard (no names → no enforcement; with names → no anonymity). | Not enforced cryptographically (L7). The demo accepts multiple submissions. |
| Spam / external-actor resistance | High (sign-in wall). | High. | Low (anyone can drop paper in the box). | Medium: a non-eligible actor cannot produce a valid proof (soundness). |
| Setup cost | Trivial. | Trivial. | Trivial. | Moderate (key issuance per student; eligible-set management). |
| Trust model | Trust Google + the form owner. | Trust Microsoft + the form owner. | Trust whoever handles the paper. | Trust the parameter setup, the random-oracle model, and that the admin does not correlate via metadata. |
| Anonymity set | All respondents (potentially identifiable individually). | All respondents. | All respondents (subject to handwriting / content leakage). | The eligible set `S` (e.g. all students in a course). |
| Suitable for sensitive feedback? | Only if students trust the form owner. | Only if students trust the form owner. | Marginal. | Yes — *if* the assumptions in §6.2 hold and the limitations in §6.3 are acceptable. |

### 7.1 Benefits of AnonFeedback (within its stated scope)

1. **Technical anonymity at verification time.** Unlike Google/MS Forms,
   where the form owner can re-identify respondents from backend records,
   AnonFeedback's verification path consults only the public set `S`. There
   is no backend record tying a feedback to an identity.
2. **Eligibility without identity.** Unlike physical forms (where eligibility
   is weak) and identified online forms (where eligibility costs anonymity),
   AnonFeedback gets both: a non-eligible actor cannot produce a valid proof,
   but a valid proof does not reveal which eligible student produced it.
3. **Inspectability.** The ZKP transcript is small, structured, and
   verifiable by anyone with the public parameters. A student can verify
   that the college's acceptance was correct (and a third-party auditor can
   re-verify the stored proofs).
4. **Educational transparency.** Every line of the cryptographic core is
   auditable. This is the opposite of "trust the platform."

### 7.2 What AnonFeedback does NOT improve over Google Forms

- **Network metadata.** Google Forms sees your IP; so does AnonFeedback.
- **Small classes.** If only three students are eligible and one submits,
  anonymity is weak — same as any system.
- **Self-identifying content.** Same problem everywhere.
- **Operational convenience.** Google Forms is one click; AnonFeedback
  requires issuance, secret distribution, and a slightly more involved
  submission flow.

We do not misrepresent this educational implementation as
production-grade security. The comparison table is meant to make the
trade-offs concrete, not to claim universal superiority.

## 9. Bug fixes and UI redesign (v2)

This version of AnonFeedback ships three functional fixes and a UI redesign
on top of the original prototype.

### 9.1 Bug fix — feedback board did not show accepted feedback

**Root cause.** In `static/app.js::refreshFeedbackBoard`, the line
`const { json } = await getJSON("/api/feedback")` destructured `json` from
the parsed response object. But `getJSON` returns the parsed JSON *directly*
(not an object with a `json` field, like `postJSON` does). So `json` was
`undefined`, `json.ok` threw a `TypeError`, and the function silently
aborted — leaving the board empty. The admin view worked because it used
`Promise.all` without destructuring. The backend (`/api/feedback`) was
correct throughout.

**Fix.** Single-line change: `const json = await getJSON("/api/feedback")`.
Added a defensive `!json || !json.ok || !Array.isArray(json.feedback)` guard
and a code comment explaining the bug for future maintainers. A regression
test was added (`test_e2e::test_accepted_feedback_appears_on_public_board`)
and verified end-to-end via the browser.

### 9.2 Course selection — Indian subjects + dropdown

The original config seeded American-style course names (`CS101`, `MA202`)
and let students type course names free-text via a `<datalist>`. The new
config seeds Indian college subjects (**DBMS, OS, CN, OOP, DSA**) and the
student form uses a `<select>` populated from `/api/admin/courses`. The
server independently rejects submissions for unknown courses via
`_require_known_course` (defending against direct API access that bypasses
the UI). The admin can still add more courses at runtime, which then appear
in the dropdown.

### 9.3 Duplicate submission prevention — course-scoped nullifier

The original prototype documented duplicate-submission prevention as a
limitation (L7) and did not implement it. This version implements a
cryptographically sound **course-scoped nullifier** as described in §2.5.
The construction extends the basic CDS OR proof with a Chaum–Pedersen
equality proof that ties the published nullifier `N = h^{x_k}` (where
`h = G2^{H(course)}` for a second independent generator `G2`) to the same
`x_k` whose knowledge is proved by the OR proof. This means a malicious
student cannot lie about `N` to bypass dedup — the per-component `M_j`
commitments enforce that `N` was correctly derived from the prover's actual
secret.

Properties: `N` is deterministic in (student_secret, course) for dedup,
unlinkable across courses (DDH), unlinkable across students, and not
invertible to identity (the server cannot test `N` against each `Y_j`
because `log_g(h)` is unknown). Stored with the feedback record but not
exposed on the public board; the admin sees it for audit only.

### 9.4 UI redesign

The UI was redesigned around the supplied Claude-inspired design system.
Key decisions:

- **Layout.** Desktop: 240px sidebar (brand, primary nav, "at a glance"
  feature list, footer disclaimer) + main content area (max-width 820px).
  Mobile (<880px): sidebar collapses into a sticky top bar with a horizontal
  scrollable nav row; content stacks vertically.
- **Typography.** Three custom fonts loaded via `@font-face` with graceful
  fallback stacks: `customSerif.woff2` for display headings (brand, hero
  titles, card titles, section headings), `customSans.woff2` for body /
  buttons / inputs / nav, `customMono.woff2` for proofs, public keys,
  secrets, codes. If the woff2 files are absent, the fallback stacks
  (system-ui / Georgia / ui-monospace) take over silently.
- **Color.** Warm light palette (`#faf9f5` background, `#ffffff` surfaces,
  terracotta `#c6613f` accent) carried over verbatim from the supplied
  tokens. Status colors (success / warning / danger) added with matching
  soft backgrounds and borders for callouts and result blocks.
- **Components.** Reusable `.card`, `.btn` (+ variants), `.input`,
  `.textarea`, `.select`, `.badge`, `.chip`, `.callout`, `.pill`,
  `.feedback-item`, `.role`, `.eligible-set`, `.table` — all derived from
  the supplied design system and adapted to the app's needs.
- **No flashy effects.** No gradients, no glows, no animations beyond
  subtle 120–180ms transitions on hover/focus. `prefers-reduced-motion`
  is respected.
- **Responsive.** Tested at desktop (1280×900), tablet (880×narrow), and
  mobile (390×844, iPhone 14 dimensions). All pages render cleanly with no
  console errors.

## 10. Honest summary

AnonFeedback is a working demonstration of how a 1-out-of-n ZKP can give a
college a *technical* (not merely policy-based) guarantee that feedback
eligibility is checked without linking feedback to identity. The
cryptographic core is a real, well-studied construction (CDS OR-proof with
Fiat–Shamir), extended with a Chaum–Pedersen equality proof for a
course-scoped nullifier, implemented transparently in pure Python.

The demo's anonymity properties hold **within the stated security model**
(§6.2) and **break down outside it** (§6.3): IP tracking, timing correlation,
small anonymity sets, identifying content, and a malicious admin who
correlates metadata can all defeat the unlinkability. These are not bugs in
the implementation — they are inherent limitations of any anonymous-feedback
system that does not also anonymize the network layer and the human-content
layer.

The project's value is in making the cryptographic workflow concrete and
inspectable. It is not, and does not claim to be, production-ready.
